# Разбор сообщений Telegram-группы

Реализация: `internal/tgparse/tgparse.go` (версия `1.0.0`). Тесты: `internal/tgparse/tgparse_test.go`.
Корпус: `testdata/telegram_corpus.jsonl` — 5 619 реальных сообщений-событий из группы (январь–10.10.2026) + 400 «посторонних».

Текущие результаты на корпусе: тип 100 %, диапазоны пропусков совпадают с эталоном 98,3 %, в ручную очередь уходит 1,0 %.

## Поток
1. Бот (privacy mode **выключен**, админ группы) получает каждое сообщение → `tg_messages` (raw JSON, `message_id`, `from_id`, `date`, `edit_date`).
2. Правка сообщения (`edited_message`) → обновляем текст, перезапускаем разбор, старые события помечаем `superseded`.
3. Удаление сообщения бот не видит — для этого есть ручная отмена в UI.
4. Автор → сотрудник: `tg_aliases` (по `from_id`, затем по username, затем по строке ФИО в сообщении). Не найден → очередь «Кто это?».
5. `tgparse.Parse(text, sentAt)` → `Result`. `Status=manual` → очередь ручной разметки в UI (`/admin/review`).

## Типы сообщений
| Тип | Признак | Что создаём |
|---|---|---|
| `absence` | слово «пропуск» | события по диапазонам времени |
| `arrived` | сообщение целиком `upd` | отметка прихода, `ArrivedAt` = время отправки |
| `sick` | «больнич…» | событие `sick` на даты из текста, иначе на день сообщения |
| `vacation` | «отпуск» | событие `vac` на каждый рабочий день диапазона |
| `none` | ничего из перечисленного | только хранение |

Приоритет: upd → больничный → отпуск → пропуск.

## Нормализация (до поиска времени)
- все виды тире `– — ‒ −` → `-`; `--` → `-`; `-:` → `-`;
- `;` между цифрами → `:` (`9;00` → `9:00`), `: ` внутри времени → `:`;
- «с 9:00 до 10:00» → `9:00-10:00`; «примерно/около/~» убираются;
- хвост Telegram `\nedited 9:41` отрезается.

## Варианты записи времени (все покрыты тестами)
| Запись | Понимаем как |
|---|---|
| `9:00-10:00`, `9:00 - 10:00`, `9:00–10:00` | 540–600 |
| `9-10` | часы: 540–600 |
| `9.00-9.30` | 540–570 (если обе части не похожи на даты) |
| `9:00:9:30` | опечатка-двоеточие: 540–570 |
| `9:00-9-30` | дефис в минутах: 540–570 |
| `9:00 9:30` | два времени через пробел |
| `9-10:30` | 540–630 |
| `17:00` (одно время) | ушёл в 17:00 → 1020–1080 |
| несколько диапазонов в строке/строках | несколько событий |

## Классификация диапазона [A, B]
- A ≤ 9:05 и B ≥ 17:55 → `day`, 480 мин;
- A ≤ 9:05 → `late` (опоздание), минуты = B − 540;
- B ≥ 17:55 → `early` (ушёл раньше), минуты = 1080 − A;
- иначе `mid` (отлучка), минуты = B − A.
- «бс» / «без содержания» → `Unpaid=true`.

## Даты
`05.10`, `5/10`, `05.10.2026`, `05.10.26`, диапазоны `12.10-16.10`, `12-16.10`. Год не указан → год сообщения; если дата получается > 183 дней в прошлом — следующий год (отпуск на январь, написанный в декабре). Нет даты → день отправки. Выходные и праздники (`holidays`) из диапазонов отпуска исключаются.

## Отработка (строка с «отработ…»)
`today` (сегодня), `tomorrow` (завтра), `yesterday` (вчера/заранее), `schedule` (по расписанию — учёба), `saturday` (суббота), `date` (конкретная дата), `unpaid` (бс), `other` (свободный текст). Текст сохраняется всегда.

## Причина
Строка «Причина: …» или оставшаяся строка после ФИО/пропуска/отработки. Категория по словарю: `study`, `health`, `family`, `personal`, `other`. «По расписанию» без причины → `study`.

## Согласовано
`@username` в сообщении → `approved_by` (обычно тимлид).

## Ручная очередь
`absence`, в котором не нашли ни одного диапазона и ни одной даты → `manual`. Админ в UI вводит события руками; ручная правка имеет приоритет над парсером и не перетирается при `reparse`.

## Как добавить новый вариант
1. Добавить кейс в `TestVariations` (падает).
2. Поправить нормализацию/регулярку, поднять `Version`.
3. `go test ./internal/tgparse/` — корпусные пороги не должны просесть.
4. `reports reparse --since 2026-01-01` на сервере.
