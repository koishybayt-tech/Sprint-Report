# Безопасность и доступы

## Секреты
- Только в `.env` на сервере (права 600, владелец — deploy-пользователь). В git — только `deploy/.env.example`.
- `JIRA_PAT` — персональный токен сервисного пользователя Jira с правом только чтения нужных проектов. Создаётся в Jira: Профиль → Personal Access Tokens.
- `BITRIX_API_KEY` — ключ API отпусков Bitrix. Передаётся в query (`api_key=`), поэтому маскируется во всех логах, ошибках и выводе `reports bitrix probe`; URL с ключом никогда не логируется целиком.
- Локальный запуск для офисной сети (`docker-compose.local.yml`): api и web слушают только 127.0.0.1, снаружи доступен лишь сервис `gate` (Caddy, порт 80) без своей защиты — вход через пользователей сервиса.
- `TG_BOT_TOKEN`, `TG_WEBHOOK_SECRET`, `SESSION_SECRET` (32+ байта случайных).
- `SECRETS_KEY` — ключ шифрования токенов личных Telegram-ботов руководителей (AES-256-GCM, `notify_settings.tg_token_enc`). Токен бота в API не возвращается и в логах не пишется; привязка бота к человеку — только по одноразовой ссылке `t.me/<бот>?start=<код>`, остальным бот отвечает отказом.
- Ротация: раз в 90 дней или сразу при увольнении человека, у которого был доступ к серверу.

## Роли
| Роль | Спринты | Посещаемость | Карточка сотрудника | Снепшоты | Нагрузка ПМов | Админка |
|---|---|---|---|---|---|---|
| admin | ✓ | ✓ | все | ✓ | ✓ | ✓ |
| lead | ✓ | только свои проекты/подчинённые | свои люди | ✓ | ✓ | — |
| hr | — | ✓ | все (без задач) | — | — | очередь «Кто это?» |
| employee | ✓ (без посещаемости других) | только своя | только своя | — | — | — |

Модули шапки (Спринты, Контроль спринта, Посещаемость, Сотрудники) пользователю выдаёт admin галочками в «Настройках» (`users.modules`): доступ есть, только если роль допускает модуль и он выдан; admin видит все модули всегда. Проверка и в шапке, и в API (`requireModule`, ответ 403).

Вход — логин и пароль пользователя сервиса (`users`, bcrypt, cookie `adata_session` httpOnly + SameSite=Lax, 14 дней; изменяющие запросы — только `application/json`). Пользователей и роли ведёт admin в «Настройках»; первый admin — `reports users add --role admin`. Пароль не короче 10 символов; смена пароля и блокировка закрывают сессии; последнего активного admin снять нельзя. Позже к тем же пользователям добавится вход через Telegram (`ADMIN_TG_IDS`).

## Персональные данные
- Посещаемость и причины отсутствий (в т.ч. здоровье) — чувствительные данные. Причины показываем только admin/hr и самому сотруднику; lead видит тип и минуты, без текста причины.
- Репозиторий приватный: в `seed/`, `testdata/`, `design/prototypes/` реальные ФИО.
- Хранение сырых сообщений Telegram — 2 года, потом удаление текста (события остаются).
- Аудит: таблица `audit_log` — кто смотрел карточку сотрудника/посещаемость и кто правил события вручную.

## Сеть
- Наружу открыты только 80/443 (Caddy). Postgres без внешнего порта.
- Если Jira доступна только из офисной сети/VPN — сервер должен быть внутри неё или иметь туннель; иначе worker не сможет синхронизироваться.
- Вебхук бота проверяет `X-Telegram-Bot-Api-Secret-Token`; остальные `/api` требуют сессию.
- Rate limit на вход: 5 неудачных попыток на логин за 10 минут, дальше 429.

## Бэкапы
`deploy/backup.sh` — ежедневный `pg_dump` с шифрованием `age`, хранение 14 дней локально + копия во внешнее хранилище. Раз в месяц — тестовое восстановление.
